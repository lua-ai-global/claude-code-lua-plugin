Local code changes reach them only after `lua push browser` and `lua push agent` (`/lua-push`). The agent needs `browser: true` or at least one named browser, or every call is a 409 `BROWSER_DISABLED`. ⏳ **lua-cli 3.49.0 or later** — below it `lua browser` and `lua browsers` do not exist (exit 1); ⏳ **3.49.2** checks the flags locally before any request; ⏳ **3.57.0** adds `--login`; ⏳ **3.58.0** adds the files and page-script settings (`maxDownloadMb`, `allowedMimeTypes`, `allowScripts`) a run's browser may carry.

Writing a named browser is `/lua-new browser <name>` (the builder writes the `LuaBrowser` and registers it in `browsers: [...]`); pushing it is `/lua-push browser`. This slash drives what is already on the server.

## Step 0 — preflight (no prompt)

1. `Bash(lua --version)` → remember `V`. Below 3.49.0, say `/lua-update` first and stop — nothing in this slash exists there.
2. Auth: `Bash(lua models list --json --ci)` — a 1–2 s authenticated call. Exit 0 or 10 = authenticated (10 = a typed key scoped away from the model catalog; fine). Exit 9 = not authenticated: use the **Skill tool** with `skill: "lua-auth"`, then re-probe; if still 9, abort with the CLI error verbatim. Exit 11 = the Lua API is unreachable: abort with that line (do not start a login). Do not use `lua agents` as the probe.
3. `list` and `delete` need a project (`lua.skill.yaml`) — they take no `--agent-id`. Missing ⇒ say "Run `/lua-init` first (browsers belong to an agent)" and stop. `read` and `run` need a project **or** `--agent-id <id>`.

## Step 1 — collect what is missing (single permission per §3.7)

Parse `$ARGUMENTS`. Whatever is still missing for the chosen verb, AskUserQuestion **once**, with every question in the same call. Never ask twice, and never ask for anything the verb does not take.

- "What do you want to do?" (options: `read` (one page, cheapest — one short session, no model calls), `run` (a task in plain words — a session plus a model call per step, and it acts on the site), `list`, `delete`)
- `read` only: "Which URL?" (free-text, an absolute `http://` or `https://` address) and optionally "Wait for anything first?" (`load`, `networkidle`, or a CSS selector such as `.price`) and "Only one element?" (free-text CSS selector; default the whole `body`)
- `run` only: "What should the browser do?" (free-text, one task in plain words — quote it on the command line), "Which page does it start on?" (free-text URL; without it the run has no start page and no domain to stay on) and optionally "Cap it?" (`--max-steps` 1–60, default 25; `--max-cost` 0.01–10 USD, default 1) and "Sign in with one of your saved logins?" (free-text name, repeatable up to 5 — ⏳ 3.57.0; only logins the user saved for this agent themselves)
- `delete` only: "Which browser?" (free-text name; if the user does not know it, run `list` instead and stop — that is a different, cheaper answer, not a second question)
- Never ask for a password, a username or a verification code. There is no flag that takes one: the person types them on a Lua page and the browser fills them in (browser.md §5).

## Step 2 — run (the Bash permission prompt IS the confirmation for a run and a delete)

`lua browser read` and `lua browsers list` sit in the `allow` tier of the plugin's permission template (installed by `/lua-doctor`) and run at once: a read opens one session, prints the page and closes it, and changes nothing at the other end. `lua browser run` and `lua browsers delete` sit in the `ask` tier, so Claude Code shows the exact command and waits — a run clicks, types and can submit on a real third-party website, spends up to `--max-cost` on the model, and with `--login` acts as the person on that site, and none of it is undone by any Lua verb. Do **not** add an AskUserQuestion on top of that prompt — it would prompt twice. (If the project has no `.claude/settings.json` rules yet, say so and point at `/lua-doctor` rather than running unprompted.)

- **read** → `Bash(lua browser read <url> [--selector <css>] [--format text|html] [--wait-for <load|networkidle|<css>>] [-e production] [--agent-id <id>])`. Keep the plain form: with `--json` the CLI prints `{ engine, data, error?, code? }` and **exits 0 even when the read failed**, so the exit code proves nothing — add it only when the user asked for the raw envelope or a single field (`--json | jq .data.title`), and then read `error` / `code` yourself. The read has 60 seconds.
- **run** → `Bash(lua browser run "<task>" [--start-url <url>] [--schema <file.json>] [--max-steps <n>] [--max-cost <usd>] [--login <name>] [-e production] [--agent-id <id>])`. Repeat `--login` once per login, at most 5. Same `--json` trap as `read` (a `run` that did not complete still exits 0 under `--json`), so prefer the plain form — it prints a `step N: …` line as each step arrives and then the result block.
- **list** → `Bash(lua browsers list)` — always spell the verb: a bare `lua browsers` (which the CLI also treats as `list`) matches no rule and would prompt.
- **delete** → `Bash(lua browsers delete --browser-name <name>)` — there is no `y/N` to skip, so no `--force`; the Bash prompt is the confirmation. Say in the same turn that the CLI also removes the row from `lua.skill.yaml`, and that the user must delete the `LuaBrowser` from the agent's `browsers: [...]` and push again — otherwise the next `lua push` recreates it. Every call naming that browser fails with `BROWSER_PROFILE_NOT_FOUND` until then.

`-e sandbox` (the default) or `-e production` only **tags the log rows**; the browser, its policy and the cost are identical. Add `--agent-id <id>` only outside a project directory, when the user named the agent. A `--schema` file must exist locally and hold a JSON Schema object.

## Step 3 — present

- **read** → `Title`, `URL` (plus `Requested` when a redirect moved it), `Status: HTTP <n>` when it was not 200, `Matches: <n>` when a `--selector` was used, `Engine` (`local` the person's desktop browser · `cloud-agent-browser` the Lua cloud browser · `cloud` Browser-Use), then the content — summarise it, never paste the whole page (it is capped at 100,000 characters, and `(content was cut short)` means it was cut or that not every match was read). `Blocked: yes (login_required|bot_wall, …)` with `Guidance:` is the page refusing an automated browser, not a bug: relay the guidance — a sign-in wall wants a saved login (browser.md §5) or a public URL, a bot wall wants the person's own desktop browser or a different source.
- **run** → `Status: <completed|failed|stopped> (<stopReason>)`, `Steps`, `Cost: $<n>`, `Engine`, `Final URL`, then `Output:`. Read `stopReason` before anything else: `done` finished · `max_steps` / `cost_cap` / `timeout` hit a cap (say which and offer a higher `--max-steps` / `--max-cost`, never silently re-run) · `confirmation_required` means an action in the agent's `confirmActions` is **held** and the run stopped — name the action and say a person approves it from their next message in the chat (a held action is dropped after 60 seconds and `lua browser run` cannot approve one) · `needs_verification` means the site asked for a code or a check and Lua emailed the user a private link to finish it in the same browser — tell them to open it and do not retry · `repeated_action` is the same action three times on a page that did not change (the task is too vague for the page: give it a `--start-url` closer to the answer, or fewer steps described more concretely) · `schema_mismatch` means the output did not match `--schema` (`BROWSER_OUTPUT_SCHEMA_MISMATCH`) · `cancelled` is a Ctrl-C.
- `BROWSER_BOT_WALL` in `Error:` is a captcha or bot check the run could not get past. The fix is the agent's own code, not a retry: `fallback: 'browser-use'` (the default) retries a blocked page once on Browser-Use, but `allowedDomains`, `fallback: 'none'` and `engine: 'agent-browser'` all switch that off — say which one is set and that widening the engine trades the domain allowlist for the fallback (browser.md §7). Otherwise the page needs the person's desktop browser or a public source.
- Always end with the rows: `lua logs --type browser` (`/lua-logs`, type `browser`) — one row per session opened and closed, per command, per `agent.step`, plus `navigation`, `blocked`, `wall`, `fallback`, `confirm`, the login rows and `download` / `upload` / `script`. That is where the engine, the refused host and the wall are recorded; read it after every failure before changing any code.
- **list** → one line per browser: name, engine (`auto` when unset) and allowed domains (`all public hosts` when unset). No browsers at all: say so and point at `/lua-new browser <name>` then `/lua-push browser`. The list shows what is **on the server** — a `LuaBrowser` in local code that was never pushed is not there.
- Exit codes: `0` ok · `1` the browser could not read the page, the run did not complete, or the CLI stopped waiting (a run has 5 minutes and the CLI waits 6 — read the rows to see how far it got) · `2` usage, checked before anything is sent (⏳ 3.49.2: a bad `-e`, `--format`, `--max-steps` outside 1–60, `--max-cost` outside 0.01–10, a URL or `--start-url` that is not `http(s)`, an empty task, a `--schema` file that cannot be read or is not a JSON object, more than 5 `--login` names or a name that is not lowercase letters, digits, `-` or `_`; also `delete` with no name, which lists the agent's browsers) · `3` not found (an unknown browser name) · `9` not authenticated · `10` refused — the key cannot run the browser for this agent (403; it needs `agents:write` on it), the network firewall blocked the request before it reached Lua (403), the agent has no browser (409 `BROWSER_DISABLED` — add `browser: true` or a `LuaBrowser`, then `/lua-push`), or **two CLI reads or runs are already going** (429 `BROWSER_CLI_CONCURRENCY`: wait for one, or Ctrl-C it; a slot frees itself within 6 minutes) · `11` unavailable — CLI runs are paused for a moment (503 `BROWSER_CLI_LIMITER_UNAVAILABLE`), the cloud browser is not configured in this environment (503 `BROWSER_WORKER_NOT_CONFIGURED`), or a network error · `130` the user pressed Ctrl-C, which cancels the run **on the server** (the CLI prints whether the server confirmed it).
- A run that answers `BROWSER_OUT_OF_CREDITS` opened nothing: the workspace has no credits or actions left. `BROWSER_BILLING_UNAVAILABLE` and `BROWSER_SESSION_STORE_UNAVAILABLE` also opened nothing — try again shortly. Neither is a code problem.
- A browser is **agent configuration, not a deploy**: nothing here goes through `/lua-deploy`. A new or edited `LuaBrowser` reaches the server with `/lua-push browser` (which confirms once, because a browser is not versioned — the push rewrites the live policy of a browser the agent already lists) and is linked to the agent by `/lua-push agent`.
